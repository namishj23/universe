## 2. Summary
Module D is complete on the backend and in a browser-side library. `packages/wellbeing-core` processes raw browsing events, rules and focus sessions on the user's device: it sanitises events down to a host name, categorises them with user rules, runs pause/resume/stop focus sessions, computes duration, context switches and distracting time, and turns all of it into daily category totals. The server only ever receives those totals, plus the user's settings. It offers consent per category, pause, see my data, export and delete everything, all to the owner only, with nothing logged or audited. Every value on the design's Wellbeing screen comes from the API. 36 new API tests and 86 library tests pass with every earlier test, and there is no drift. A platform-wide time-zone bug was found and recorded for P8 (not in P5's scope to fix).

### Problem statement → where it is satisfied

| Requirement | Satisfied by |
| --- | --- |
| 1. Start and stop a user-controlled focus session | `startSession`, `pauseSession`, `resumeSession`, `stopSession` in `packages/wellbeing-core/src/session.ts` (pure, typed errors; U2 keeps the session in IndexedDB) |
| 2. Categorise sample browsing events using user-defined rules | `sanitiseEvents` + `validateRules` + `compileRules`/`classify` (`events.ts`, `rules.ts`), `DEFAULT_RULES` editable; sample events in `samples/day-*.json` |
| 3. Display focus duration, context switches and time on user-designated distracting sites | `computeMetrics` (`metrics.ts`): `activeMs`, `sessionMs`, `switches`, `distractingMs` (only sites the user marked), `categoryMs`, `domains` |
| 4. Pause, data inspection and deletion controls | `POST /api/wellbeing/tracking` (pause/resume/off), `GET /records` (see my data), `GET /export`, `DELETE /records/:date/:category`, `DELETE /records?from=&to=`, `DELETE /data`; locally, the per-domain breakdown |
| 5. Process locally; never collect page contents, credentials or unnecessary personal information | Raw events, URLs, domains, rules and sessions are processed only by `wellbeing-core` in the browser. The sanitiser keeps `{ at, kind, domain }` (no path, query, credentials, titles or content; IPs become `local`). The only upload is `PUT /totals` (`{ date, category, minutes }`, strict: a `domain` field is a 400). The server never logs or audits wellbeing values. |

"Process locally" means: the browser holds the raw events (sanitised before storing) and computes everything. The server is a store for daily category totals the user chose to share by turning tracking on, and it can't reconstruct which sites were visited.

## 6. Decisions made
- Privacy architecture: raw events, domains, rules and sessions stay in the browser (`wellbeing-core`); the server stores daily category totals, settings and weekly-summary markers only; owner-only access.
- No wellbeing audit entries; wellbeing request logs carry method + route pattern only; unexpected errors are scrubbed of messages before the platform logs them.
- Metrics model: attribution to the earliest of next event / idle cap / pause start / session end; a pause forgets the current domain; active time = counted time covered by activity windows. Chosen so "categories ≤ active" and "pausing never increases any total" hold.
- Rounding: per day, half-up total, largest remainder across counted categories; zero rows included.
- `*.x.com` matches `x.com`; IPs and localhost → `local`.
- Summary totals count only currently counted categories; stored rows of a category turned off stay and are flagged `counted: false`.
- Uploads lock the settings row and check tracking, categories, dates and the 1440 cap in one transaction.
- `platform.schedule` registers only; the server starts and stops the timers.
- Delete everything also removes weekly-summary markers and sets tracking `off`.
- `studyMinutesThisWeek` returns null unless the caller is the user, sharing is on and study is counted.
All are in `PROGRESS.md` (Decisions and Open questions).

## 9. Security and performance review
- **Validation:** every body, query and param is parsed with a strict Zod schema; routes without a body or query reject any (`NoQuery`). Uploads reject unknown fields (`domain`, `url`), duplicates and > 31 days.
- **Ownership:** no route takes a user id; every query is scoped to the session user. Admin, driver and invigilator get 403 on all 10 routes (outer guard); another student gets 404 or empty results (tests).
- **SQL:** Prisma or tagged `$queryRaw`/`$executeRaw` only; arrays via `unnest` parameters.
- **CSRF:** all changes need the header (test). `DELETE /data` also needs `{ confirm: 'DELETE' }`.
- **Logging/audit:** no wellbeing audit entries; request logs keep method, status and route pattern only; other errors are scrubbed; a captured-logger test checks no value, date, category, domain or query string appears. Weekly-summary payload has no numbers.
- **Caching:** `Cache-Control: no-store` on every wellbeing response, errors included.
- **Concurrency:** uploads, tracking changes and delete-everything lock the user's settings row; four concurrent 500-minute uploads → exactly two stored.
- **Uniqueness:** primary keys stop duplicate day/category rows and duplicate weekly summaries (the job is idempotent across instances).
- **Indexes/paging:** PK serves user date ranges; `date` index serves the job; records are cursor-paged (default 20, max 100); export is unpaged but bounded (≤ 365 days × 5 rows).
- **Shutdown:** scheduled jobs stop on SIGTERM/SIGINT with the other timers.
- **Not met / open:** the platform-wide time-zone shift (HIGH, for P8): wellbeing reads back no database-clock values, but platform activity timestamps (`created_at` defaults) are affected the same way as everywhere else.
