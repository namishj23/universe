## 6. Decisions made
- **Data model:**
  - `hub_profiles` is the hub's person row, created on first use. One back-relation on `User`.
  - The progress row stores a copy of the topic's total, with a composite FK `ON UPDATE CASCADE` and a CHECK `0 ≤ solved ≤ total`.
  - Resource file ids have no FK to `files`, as in rides.
- **No drift:** the schema uses PostgreSQL's normalised predicate and generation text.
- **Search:**
  - words as written plus English stems; `simple` prefix queries; one statement, FTS UNION ALL uploader names;
  - 60 searches per minute per user.
- **Shared week:** `weekOf()` in contracts (Sunday 00:00 to Saturday 23:59:59.999 Asia/Kolkata). Other modules should use it.
- **Ranking:**
  - formula and weights as the prompt, in `config.ts`;
  - `slotsThisWeek` counts the next 7 days;
  - ties within 1e-9 go to more slots, then name;
  - the reason says "Covers two of your weakest topics: …" when a mentor covers two of three.
- **Requests:**
  - either party cancels; cancelling an accepted request reopens a future slot;
  - a taken requested slot is 409 `SLOT_TAKEN`;
  - complete only after the session has started;
  - lock order: mentor profile, then request, then slot.
- **Prep:**
  - increments outside 0..total are 409, not clamped;
  - goal target = this week's row, else the latest earlier one, else 20;
  - the series is worked backwards from current totals, counting events only from when a topic was tracked.
- **Resource visibility:**
  - hub role AND (attached to a live resource, or uploader, or admin);
  - `inUse` counts deleted resource rows too.
- **Idempotency:** in-process TTL map, 10 minutes, max 10,000 keys (single-instance limit).
- **Admin ranking:** demand-weighted W3 (Σ solved ÷ Σ total per topic over students) and the union of students' interests.
- **Definitions:** a term is Jan–Jun or Jul–Dec IST; near capacity is ≥ 80 %; new resources means the last 7 days.

All of these are in PROGRESS.md (decisions, and "Open questions" marked "decided … (P4, unattended)").

## 9. Security and performance review
- **Validation:**
  - Every body, query and param goes through a strict Zod schema in `packages/contracts/src/hub/index.ts`. Routes without a query reject any query string.
  - Name and email can't be written. Uploads are checked from their bytes by the platform: a renamed ELF gets 415.
- **SQL:** only Prisma and tagged-template `$queryRaw`.
  - Optional filters use `(${x}::type IS NULL OR …)` parameters. Nothing is concatenated into SQL.
  - Search input is reduced to letters and digits before it becomes a tsquery, and LIKE wildcards are escaped. Tests cover wildcards and injection strings.
- **Role and ownership:**
  - The outer guard admits student, mentor and admin; each route narrows the role.
  - Requests and slots return 404 to non-parties, and student cards are shown only to a requested mentor or an admin.
  - Resource files need a hub role, so drivers and invigilators get 404. Unattached files stay owner-only. Admin routes refuse everyone else.
  - Every rule is tested.
- **Concurrency:**
  - Accepting a request is one transaction with row locks (profile → request → slot) and re-checks. The race and capacity tests pass.
  - The database backs this up: one live request per pair (partial unique), no overlapping live slots (exclusion constraint), no double start (partial unique), `solved` within bounds (CHECK), one resource per file (unique).
- **Rate limits:** search is limited to 60 per minute per user. Uploads use the platform's limiter.
- **Errors:** every error is an `ApiError` with a code (`SLOT_TAKEN`, `NO_OPEN_SLOT`, `MENTOR_FULL`, `REQUEST_EXISTS`, `PROGRESS_OUT_OF_RANGE`, `FILE_ALREADY_ATTACHED`, …), in the standard error body.
- **Privacy:**
  - Activity payloads carry ids, names, the note and the session time, never skills, goals or progress.
  - The audit entry for an admin deleting a resource holds only subject, type and whether it was the admin's own.
- **Secrets and config:** no new environment variables; constants live in `config.ts`.
- **Performance:**
  - Indexes on every FK and on every filter or sort column; the EXPLAIN results are in §8.
  - Every list is cursor-paged (default 20, max 100). The ranked mentor lists use an offset cursor (bounded).
  - The mentor list is one candidate query (the test shows the same query count for 4 and 9 mentors). Incoming requests load student cards in two batched queries. Search is one statement.
- **Reliability:** every multi-step write is one transaction (activity is emitted after commit). The seed is idempotent.
- **Not met / limits:**
  - The Idempotency-Key map and the search limiter are per process (marked `ponytail:`, like the existing limiters and the SSE broker).
  - `location_stop_id` isn't checked against rides stops yet (P6).
  - Readiness weights and topic sizes are judgement calls (`docs/ASSUMPTIONS.md`).
